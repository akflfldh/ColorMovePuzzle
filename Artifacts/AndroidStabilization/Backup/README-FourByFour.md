# COLOR MOVE — 4×4 퍼즐

기존 `Assets/ColorMovePuzzle/Scenes/ColorMovePuzzle.unity` 한 씬을 유지했습니다. Play → 4×4 → 스테이지를 선택하면 플레이할 수 있습니다. 아래는 4차 개발 기록이며, 이후 추가한 5×5는 [README-FiveByFive.md](README-FiveByFive.md)를 참고하십시오.

## 구현 순서

먼저 Stage01 한 개와 실제 4×4 UI를 생성하여 PlayMode에서 16칸/색상 개수, 탭 이동·애니메이션 잠금, 재시작 및 목표 일치 클리어를 확인했습니다. **프로토타입 테스트 3/3 통과** 보고서를 `Artifacts/FourByFour/PrototypeTests.json`에 저장한 뒤 30개로 확장했습니다. 첫 번째 스테이지 에셋은 확장 과정에서 유지했습니다.

## 공통 로직과 화면

- `PuzzleBoard`의 기존 크기 기반 규칙을 그대로 사용합니다. 초록색은 enum의 맨 끝에 추가하여 기존 Black=4와 3×3 에셋의 숫자 값을 보존했습니다.
- 실제 배치는 4×4, 빨강/파랑/노랑/초록 각 3개, 검정 2개, 빈칸 2개입니다. 같은 색과 빈칸은 타일별 ID 없이 색상값만 비교합니다.
- 동일한 `PuzzleBoardView` 클래스로 3×3/4×4의 조작 격자와 목표 격자를 각각 작성했습니다. 하나의 `PuzzleGameController`가 스테이지 크기에 맞는 뷰를 선택합니다. 별도 4×4 이동·클리어·애니메이션 컨트롤러는 없습니다.
- 큰 보드는 840×840, 목표는 300×300 기준을 유지하고 4×4 셀 크기와 간격을 계산합니다. 14개 Image 타일과 16개 빈 자리 배경을 생성했습니다.
- 기존 탭/방향 스와이프, 대각선/줄 넘김 금지, 0.15초 이동과 입력 잠금, 재시작을 사용합니다.
- 단계 선택 카드 30개와 ScrollRect를 재사용하며 현재 격자 크기를 헤더에 표시합니다. 3×3의 MINIMUM 표시는 유지하고 4×4는 `RATING` / `ESTIMATED DIFFICULTY`로 구분합니다.

현재 4×4 목표:

```text
R R R B
B B Y Y
Y G G G
K K E E
```

## 생성, 평가와 한계

**4×4 전체 BFS는 사용하지 않습니다.** 목표에서 실제 합법적인 이동을 적용한 경로를 기록하고, 그 경로의 역순을 알려진 해법으로 저장합니다. 각 경로는 동일한 색상 배열을 다시 방문하지 않도록 하며, 선택된 30개 시작 배치는 서로 다르고 목표와도 다릅니다.

개발 단계에서만 실행하는 생성기의 한도:

- 고정 난수 시드 44004
- 최대 512개 경로, 경로당 최대 96회 이동
- 최대 6,000개 후보
- 후보 탐색 시간 제한 5초
- 후보는 경로 도중 여러 깊이에서 수집하고, 충분한 후보가 존재하는 등급 구간에서 선택

최종 실행에서 6,000개 후보를 수집했습니다. 후보 탐색은 약 **243ms**, 에셋 저장을 포함한 생성은 약 **1.03초**였습니다. 실제 기록은 `Artifacts/FourByFour/Generation.json`에 있습니다. 경로/후보 수로 메모리도 제한하며 전체 상태 공간이나 대규모 탐색 트리를 보관하지 않습니다.

휴리스틱은 **동일 색상 간 최소 비용 매칭 맨해튼 거리**입니다. 각 색상에 대해 현재 위치와 목표 위치 사이의 모든 가능한 할당 중 최소 합을 비트마스크 DP로 계산합니다. 가장 가까운 타일을 순서대로 붙이는 탐욕적 방식이나 같은 색 타일에 임의 ID를 붙이는 방식을 사용하지 않습니다. 색상별 타일 거리의 합과 두 빈칸의 최소 매칭 거리 중 큰 값을 하한 L로 사용합니다.

한 번의 이동은 색상 타일 하나와 빈칸 하나를 한 칸씩 옮기므로 L은 실제 최단 이동 횟수를 넘지 않는 하한입니다. 그러나 장애물/타일 간 간섭과 우회 비용은 충분히 반영하지 못합니다. 알려진 합법 해법 길이 U는 상한이며, 실제 최소 이동 횟수는 **L 이상 U 이하**입니다. **섞은 횟수나 U를 최소 이동 횟수라고 표시하지 않습니다.**

4×4 UI의 추정 등급은 L을 사용하며 순서대로 감소하지 않게 선택했습니다. 현재 등급 범위는 **4~29**입니다. 같은 등급에서는 배치의 색상 차이와 더 짧은 알려진 경로를 고려합니다. 이는 실제 최단 거리나 사람의 체감 난이도가 단계마다 반드시 증가한다는 증명이 아닙니다. 일부 스테이지에서 L=U이면 수학적으로 거리를 확정할 수 있지만, 현 버전의 4×4 데이터/UI는 보수적으로 모두 추정 등급으로 분류합니다.

`Artifacts/FourByFour/Stages.csv`에 시작/목표, 추정 등급, 하한 L, 알려진 해법 상한 U를 구분하여 기록했습니다. 모든 스테이지 해법을 실제 이동 규칙으로 검증합니다. 플레이 중에는 이 휴리스틱, 후보 탐색이나 BFS를 실행하지 않습니다. 오프라인 도구는 Editor 전용 어셈블리에 있습니다.

## 저장과 이어하기

`Application.persistentDataPath/ColorMovePuzzle/` 아래에 저장합니다.

| 파일 | 내용 |
| --- | --- |
| `progress-v1.json` | 기존 3×3 클리어/해금/마지막 선택 |
| `progress-4x4-v1.json` | 독립적인 4×4 클리어/해금/마지막 선택 |
| `menu-profile-v1.json` | 공통 마지막 플레이 격자·스테이지와 BGM/SFX 볼륨 |

각 모드는 최초 1번만 열립니다. 모드를 왕복해도 해당 모드의 저장소를 다시 사용하며, 클리어하면 그 모드에서만 다음 단계가 열립니다. Continue는 마지막 격자와 스테이지를 선택해 최초 배치부터 입장합니다. 설정값 저장 형식은 변경하지 않았습니다. 테스트와 화면 캡처는 별도 저장 폴더를 사용합니다.

## 검증과 남은 확인

단일 4×4 프로토타입 테스트를 먼저 완료했고, 확장 후 전체 EditMode/PlayMode 회귀 테스트를 실행합니다. 30개 4×4 해법은 모델로 모두 검증하고, 실제 UI/애니메이션 플레이는 1·15·30번과 입력/재시작/전환을 확인합니다. 기존 3×3 30개 연속 클리어 테스트도 유지합니다. 결과 파일은 `Artifacts/FourByFour/`에 보존합니다.

최종 자동 테스트 결과는 **EditMode 53/53, PlayMode 30/30 통과**, 실패/건너뛰기 0입니다. PlayMode는 약 78초였고 짧은 스와이프 콜백 순서 회귀도 포함합니다. 3×3 30개 연속 클리어, 4×4 1·15·30번, 양쪽 진행 파일 및 Continue를 실제 실행하여 확인했습니다.

추가 실제 InputSystem 가상 Touchscreen 검증에서 짧은 드래그가 타일 내부에서 끝날 때 클릭 콜백이 드래그 종료보다 먼저 포인터를 해제하는 기존 입력 문제가 발견됐습니다. 공용 PuzzleTileView에서 드래그 중 클릭이 포인터를 해제하지 않도록 수정하고 해당 콜백 순서의 회귀 테스트를 추가했습니다. 검증 동안 사용자 저장 파일을 변경하지 않았습니다.

수정 후 실제 가상 Touchscreen 검증도 통과했습니다. 목표 격자 읽기 전용, 탭/짧은 방향 스와이프, 재시작, 클리어/다음, 모드 왕복, 4×4 Continue 및 3×3 파일 불변을 확인했습니다. `NativeTouch.json`에 최종 성공 결과가 있습니다.

1080×1920, 720×1280, 1080×2400에서 큰 4×4 타일의 화면상 가로·세로가 같고 보드가 안전 영역 안에 있음을 확인했습니다. 기준 해상도에서 셀은 189×189입니다. 캡처는 `Assets/Artifacts/FourByFour/`, 레이아웃 수치는 `Artifacts/FourByFour/Layout-*.json`에 있습니다.

Android APK/AAB 빌드와 실기기 터치/성능은 별도 검증이 필요합니다. 5×5, 광고 SDK, 인앱 결제는 추가하지 않았습니다.
